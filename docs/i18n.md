# Internationalisation (i18n)

Kedaipal has **two parallel locale systems** that don't share a runtime, and a
single canonical `Locale` type that both of them import from
`convex/lib/locale.ts`:

1. **Paraglide (visitor-chosen cookie)** — the public marketing site. Covers
   English (`en`, base), Bahasa Malaysia (`ms`), and Chinese (`zh`) via
   [Paraglide JS](https://inlang.com/m/gerre34r/library-inlang-paraglideJs)
   (inlang).
2. **Backend locale (retailer-owned, per store)** — WhatsApp messages, emails,
   order-status labels, and the buyer tracking page. Driven by the seller's
   `retailers.locale` field, not a visitor cookie — a buyer sees the
   **store's** language, not their own browser's.

These are genuinely separate systems serving different audiences (marketing
visitor vs. a specific store's buyer) — don't assume a component under
`src/routes/track.$token.tsx` or `convex/lib/whatsappCopy.ts` goes through
Paraglide just because the rest of the site does. See "Scope" below.

## 1. Paraglide (marketing site)

- **Source of truth:** `messages/en.json`, `messages/ms.json`, `messages/zh.json`
  — flat `key → string` catalogs, one per entry in
  `project.inlang/settings.json`'s `locales` array. `en` is the base locale.
- **Compiled output:** the Paraglide Vite plugin (`vite.config.ts`) compiles the
  JSON into typed message functions under `src/paraglide/` on every `dev`/`build`.
  This directory is generated — never edit it by hand. To recompile manually:
  ```sh
  npx @inlang/paraglide-js compile --project ./project.inlang --outdir ./src/paraglide
  ```
- **Usage:** `import { m } from "../paraglide/messages"` then call
  `m.key_name()` in JSX. Keys with placeholders take an object:
  `m.cost_cta_join({ price: 104 })` for `"Become a Founding Member — RM{price}/mo"`.
- **Locale resolution** (`strategy` in `vite.config.ts`):
  `["cookie", "preferredLanguage", "baseLocale"]` — the `PARAGLIDE_LOCALE`
  cookie wins, else the browser's preferred language, else English.
- **Switcher:** the landing `Nav` (`src/components/landing/nav.tsx`) has a
  3-way dropdown (`LanguageSwitcher`) — trigger shows the *current* locale
  (EN/BM/中文), the menu lists all `locales` from the compiled runtime and
  calls `setLocale()` (writes the cookie + reloads) on pick. Every public
  landing page renders `<Nav />`, so the switcher is available on all of them.

### Scope (what Paraglide translates)

Translation covers the **public, pre-sign-in marketing site**:

- Landing page (`/`) and all its sections (`src/components/landing/*`)
- Pricing (`/pricing`)
- Cost calculator (`/cost`)

The store QR poster (`/app/poster`) also renders its `poster_*` keys through
Paraglide, but via its own explicit-locale-override toggle rather than the
visitor cookie (see `store-poster.tsx`). Its `PosterLocale` type is still
`"en" | "ms"` — the `zh` translations exist in `messages/zh.json` (every key
is translated, poster included), but widening `PosterLocale` → `Locale` and
adding the third toggle option is Phase 2/3 of `86eybjw5n`, not done here.

**Out of scope** (deliberately, for now): sign-in / sign-up / onboarding, the
legal pages, the seller dashboard (`/app/*`), and the buyer storefront
(`/<slug>` + checkout + `/track/<token>`). The seller-dashboard Settings &
Billing tabs happen to be translated as a side effect of recent work; the rest
of the dashboard, the storefront, and the tracking page are **not** on
Paraglide at all — they're on the backend locale system below, and are
tracked as a separate string-extraction sweep (Phase 2/3 of `86eybjw5n`).

### Gotcha: resolve `m.*` at render time, not module scope

`m.foo()` reads the current request's locale when called. On the SSR server,
modules are imported **once** and reused across requests, so calling `m.*` at
module top-level bakes in whichever locale was active at first import and serves
it to everyone. Always call message functions **inside** a component render (or a
hook), never in a module-level `const`. See the `useTiers`/`useFeatures` helpers
in `src/routes/pricing.tsx` for the pattern.

### Adding or changing a Paraglide string

1. Add the key to **every** `messages/{locale}.json` catalog (same key,
   same `{placeholders}`).
2. Use `m.your_key()` in the component (resolved at render — see gotcha above).
3. Recompile (auto on `pnpm dev`, or run the compile command above).
4. `pnpm test` — `src/lib/i18n.test.ts` enforces that every catalog listed in
   `project.inlang/settings.json` has an identical key set to the base
   locale, no empty values, and matching placeholders per key. It does **not**
   catch hardcoded English that never goes through `m.*` — that's a
   code-review concern. A quick sweep:
   ```sh
   # user-facing JSX string literals in an in-scope file that bypass m.*
   rg '>[A-Z][a-z]' src/routes/pricing.tsx
   ```

### Naming conventions

Keys are `snake_case`, prefixed by surface: `nav_*`, `hero_*`, `faq_*`,
`pricing_*` (landing pricing teaser), `pricingpage_*` (the full `/pricing`
route), `cost_*` (the `/cost` calculator), `footer_*`, `poster_*`, etc.

## 2. Backend locale (WhatsApp, email, order status, tracking page)

- **Source of truth for the type:** `convex/lib/locale.ts` exports the
  canonical `Locale = "en" | "ms" | "zh"` union, `LOCALES` (an array in the
  same order), and `pickLocale(input: unknown): Locale` (unknown/missing input
  → `"en"`). Every copy catalog below imports `Locale` from this one file
  (directly, or re-exported through `whatsappCopy.ts` / `emailCopy.ts` /
  `orderStatus.ts` for backward-compatible import paths) — there is
  deliberately **one** place a 4th locale gets added, so a lookup that forgets
  the new key is a compile error (`Record<Locale, …>` missing a property),
  never a silent English fallback.
- **Which locale a message uses:** the **retailer's** `retailers.locale`
  field (`Settings → Store → "WhatsApp message language"`), *not* the
  buyer's browser/cookie. A buyer from Perak messaging a Chinese-speaking
  Penang stall sees the seller's chosen language, because the seller — not
  the buyer — is the one authoring/reading the reply on their end too.
- **Catalogs:**
  - `convex/lib/whatsappCopy.ts` — WhatsApp message bodies (`waCopy`,
    `systemMessages`, pickup/delivery-fee labels, `poweredByLine`,
    `privacyNoticeLine`). Per-retailer overridable subset via
    `messageTemplates` (schema + `retailers.ts` validators); the
    non-overridable "system" messages always use the built-in catalog.
    **This catalog shrank a lot in `86eyd63r8`** (one message per order): the
    `status` catalog (packed/shipped/delivered/cancelled), `renderStageUpdate`,
    `hasTemplateOverride` and the `paymentReceived` / `paymentDue*` /
    `paymentReminder*` / `deliveryFeeSet` / `deliveryPhotoCaption` /
    `orderReceiptCaption` / `orderInvoiceCaption` system messages were all
    deleted along with the sends that rendered them. **`TEMPLATE_KEYS` is now
    `["confirm"]`** — a single overridable message — so the per-locale template
    editor is one textarea per language, not a set. Everything those messages
    used to say now lives on `/track/<token>`, which is **not** a localised
    surface yet (see the Track page bullet below — that gap widened with this
    change). See [`one-message-per-order.md`](./one-message-per-order.md).
  - `convex/lib/emailCopy.ts` + `convex/lib/billingEmailCopy.ts` — retailer
    order-event and billing emails.
  - `convex/lib/orderStatus.ts` (+ client mirror `src/lib/orderStatus.ts`,
    kept in lockstep by hand — see the file's own header comment) —
    short status labels, transition-button copy, and Phase-2 custom
    `orderStages` (per-stage `label`/`description`, each `{ en: string; ms?:
    string; zh?: string }`).
  - `convex/lib/wabaLimits.ts` — inbound opt-out/opt-in keyword matching
    (`classifyOptOutKeyword`); EN/MS/ZH keywords each map to their own
    `OptOutSource` so the audit trail records which language triggered it.
- **Fallback semantics:** every retailer-authored override (message
  templates, status labels, stage labels/descriptions) is looked up **per
  locale, independently** — switching the store's locale to `zh` when only
  `en`/`ms` overrides exist falls straight through to the **default zh
  catalog**, never to a leftover `en`/`ms` override (there is no cross-locale
  override fallback, only override → built-in-default fallback within the
  same locale). Verified by `convex/retailers.test.ts` /
  `convex/lib/orderStatus.test.ts`.
- **Track page:** `src/routes/track.$token.tsx` reads `order.retailerLocale`
  (frozen at order-create time from the store's locale) and resolves labels
  through `src/lib/orderStatus.ts`. It is **not** a Paraglide surface (see the
  correction note above) — full string-extraction for the tracking page is a
  Phase-2 follow-up.
  **This follow-up got materially more important in `86eyd63r8`.** The tracking
  page is now the *only* place a buyer learns anything after their single
  confirmation — status, how to pay, mockup approval, courier and tracking
  number, delivery photos, the receipt. Every one of those used to arrive as a
  WhatsApp message rendered from a fully `Record<Locale, …>`-typed catalog; they
  now arrive on a page whose own strings are largely hardcoded English ternaries.
  A BM- or zh-locale store's buyer is therefore **less** well served in their
  language than before, not more. Localising this page is the highest-value item
  left in Phase 2.

## CJK font fallback

Neither `Red Hat Display Variable` (headings) nor `Geist Variable` (body) —
the only two webfonts this project bundles — ships CJK glyphs. Without an
explicit fallback, `zh` text would silently drop to the browser's unstyled
system default the moment the landing switcher (or a `zh`-locale store) made
Chinese text reachable. `src/styles.css`'s `--font-heading` / `--font-sans`
now append `'PingFang SC', 'Microsoft YaHei', 'Noto Sans SC', sans-serif`
after the Latin webfont — **system-installed CJK fonts, zero bytes**,
covering macOS/iOS, Windows, and Android/Linux respectively. We deliberately
did **not** bundle a CJK webfont (e.g. `@fontsource-variable/noto-sans-sc`):
subset or not, a CJK font adds real weight for a locale that's still ramping,
and the system-font fallback already reads clean. Revisit if a native-speaker
review flags the system-font look as inconsistent with the brand.

## Add a locale — checklist

Adding a 4th locale touches both systems above. Everything a `Record<Locale,
…>` lookup is missing becomes a **TypeScript compile error** once you widen
the union in step 1 — let the compiler find the call sites for you rather
than grepping.

1. **`convex/lib/locale.ts`** — add the literal to `Locale` and `LOCALES`.
   `pickLocale` needs no change (it already narrows against `LOCALES`).
2. **Fix every compile error** this produces across `convex/lib/whatsappCopy.ts`,
   `convex/lib/emailCopy.ts`, `convex/lib/billingEmailCopy.ts`,
   `convex/lib/orderStatus.ts`, `src/lib/orderStatus.ts` (add the new key to
   every `Record<Locale, …>` catalog) and `convex/lib/wabaLimits.ts` (add an
   opt-out/opt-in keyword + `OptOutSource` variant for the new language, if
   one exists).
3. **Schema + validators:** `convex/schema.ts` (`retailers.locale`,
   `messageTemplates`, `statusLabels`, `orderStages[].label`/`.description`)
   and the matching validators + `MessageTemplatesShape`/sanitizers in
   `convex/retailers.ts` — all dev-only widens (new optional fields), no
   migration needed.
4. **Settings UI:** `src/routes/app.settings.tsx` — `LOCALE_OPTIONS` /
   `LOCALE_LABELS`, the `MessageTemplatesForm` `locales` array, the
   `StageEditor`'s per-locale label/description inputs (`StageDraft` gains a
   field, `seedToDraft`/`draftsToStages` carry it through, add the input
   pair). `src/components/dashboard/greeting-checklist-row.tsx`'s `TEMPLATES`
   catalog + a `LangButton`.
5. **Paraglide:** add the locale to `project.inlang/settings.json`'s
   `locales` array and create `messages/<locale>.json` mirroring
   `messages/en.json`'s keys. `src/lib/i18n.test.ts` picks it up automatically
   (it iterates `LOCALES`, not a hardcoded pair) — it will fail loudly if the
   catalog file is missing, incomplete, or has placeholder mismatches.
6. **Landing switcher:** `src/components/landing/nav.tsx`'s `LanguageSwitcher`
   needs no code change — it renders every entry in the compiled
   `paraglide/runtime` `locales` array — but add `SHORT_LABEL`/`FULL_LABEL`
   entries for the new locale (both are `Record<Locale, …>`, so a missing
   entry is a compile error).
7. **CJK/other script coverage:** check whether the new locale's script needs
   a font fallback (`src/styles.css` `--font-heading`/`--font-sans`) or
   `line-clamp`/`break-words` adjustments for scripts without Latin-style word
   breaks (see the CJK section above).
8. **Tests:** extend unit tests colocated with each catalog
   (`convex/lib/whatsappCopy.test.ts`, `convex/lib/orderStatus.test.ts`,
   `convex/lib/wabaLimits.test.ts`, `convex/lib/emailCopy.test.ts`,
   `convex/lib/billingEmailCopy.test.ts`) with at least one assertion per new
   locale, mirroring the existing en/ms cases.
9. Everything **explicitly out of scope for the `zh` rollout** (Phase
   1 of `86eybjw5n`) still needs its own pass for a new locale too: storefront
   string extraction, the tracking page, PDF rendering (`convex/lib/pdf/` —
   `sanitize()` currently strips non-Latin-1 characters entirely; a CJK/other
   non-Latin font needs `fontkit` + a real embedded font before this is safe),
   CSV export headers, and the `/app` dashboard sweep. See `86eybjw5n`
   Phase 2/3.
