# Shipped log (post-MVP)

Chronological record of everything shipped after the April 2026 MVP — newest first. Each entry says **what shipped, why it was built that way, what was deliberately rejected, and which trap was found**, and links to the feature doc that carries the full detail.

This log lives here, not in [`CLAUDE.md`](../CLAUDE.md), because it is reference material read on demand — not an instruction that needs to be in context for every task. It was moved out verbatim (ClickUp `86eyqh89n`) when the section had grown to **91% of CLAUDE.md**, loading ~40k tokens into every session while carrying none of the rules.

## How to add an entry

- Write the entry **in the same PR as the feature**, alongside its code, tests and docs (the standing "code + tests + docs together" rule).
- New entries go at the **top** of the list below.
- Link the feature doc that holds the detail — this log is the summary and the reasoning, the doc is the reference.
- Keep the *why*: the rejected alternative and the trap found are the parts that stop the next person repeating the mistake.
- **Do not add it to CLAUDE.md.** CLAUDE.md carries rules and pointers only.

> Seller-facing release notes are a **different artifact** — benefit statements shown in-app, authored in `src/content/releases.ts` (ClickUp `86eyqgxv9`). This log is the engineering record; that list is what a seller reads. Neither replaces the other.

- **Order workspace depth — a column registry behind the export, a table view, item thumbnails, pinned orders** ✅ (ClickUp [`86eyrtz74`](https://app.clickup.com/t/86eyrtz74), dev) — four items from a Hermoolah vendor session, shipped together because they are one story: **the inbox wasn't yet a place a seller could live in**, so they exported to Excel. **(1) The export was missing more than reported.** "Categories and address are missing" was true, but the address gap was total — there was **no destination column at all**, for delivery *or* self-collect, so a seller building a despatch manifest was working blind. Auditing turned up an arithmetic hole the file's own comments already admitted: `computeOrderTotals` folds the mockup quote into `total`, and with no quote column `Subtotal + Pickup fee + Delivery fee` **silently failed to reconcile on every made-to-order order** — a bookkeeping export that doesn't balance is the definition of "something left out". `orderCsv.ts` is now a **column registry** (36 entries: key, label, group, width, accessor) rather than a fixed string array, adding the split address, pickup outlet, custom-work quote, payment reference, paid-on, fulfilment time, order type, marketing origin, cancelled reason and fee-pending. `Subtotal · Custom work · Pickup fee · Delivery fee · Total` are kept **adjacent** so the identity checks by eye, and a test pins the adjacency. **`Categories (current)`** is deliberately a **live lookup** — categories are never frozen onto an order line ([`product-categories.md`](./product-categories.md)), so the column is what those products are filed under *today*; freezing `categoryNames` was considered and rejected (no one wants point-in-time category history, they want to pivot sales by category). **`trackingToken` is excluded and a test enforces it** — it is the buyer's tracking-page capability and exports get emailed to bookkeepers. **(2) A table view**, desktop-only. The rationale is retention, in the vendor's words: they export *"just because they are too used to excel"*, and the inbox already filtered and sorted as well as a spreadsheet — it just didn't look like one. **Two views, not three** (the card list already *is* the list view). It renders from the **same registry** as the CSV, which is what makes "the table replaces the export" true rather than aspirational; needed **zero backend** (`searchOrders` already returned full docs); and the `lg` gate is `useIsDesktop()` in **JS**, not only CSS, because `?view=table` shared from a laptop would otherwise hand a phone a 36-column table with the toggle hidden. Column visibility persists per store in `localStorage` — not the URL (36 toggles would bury the shareable bucket/filter/sort) and not Convex (a display preference shouldn't cost a write or sync to a colleague). Export in table view becomes a **two-item menu** (visible columns / all columns) rather than a **dialog** — a modal on every export taxes a path sellers hit often. **(3) Line-item thumbnails** on order detail (variant image → product image → `AppImage` fallback, batched server-side): a packing aid, so the image is deliberately **not** frozen onto the order and a deleted photo degrades to the fallback box. **(4) Pinned orders** (`orders.pinnedAt`, `seenAt` posture, never bumps `updatedAt`). Three owner calls, all counter-intuitive: **never auto-unpin** (a delivered order can still be worth keeping on top — the system doesn't get to decide the seller is finished); **a pin outranks the filter** while the Pinned chip is on, because that is what sellers pin *for* — park an order on top, filter to something else, compare — implemented as a short-circuit in `buildInboxPredicate` so the export inherits it and the CSV holds exactly what was on screen; and **pinned-first is a partition, not a third sort option** competing with newest/due. **All-tier**: a one-bit annotation is not an inbox search feature, and gating it would leave a Starter watching pinned rows sort to the top of a list they were never allowed to pin into. The design risk was never the marker but **staleness** — pins that never clear turn the top of the inbox into a graveyard, the exact failure the nav-badge fix (`86eyjfazz`) existed to prevent — so the always-visible **Pinned N** chip (tallied over the full window, leading the chip row) is the standing reminder, and clearing is **Unpin** in the existing bulk bar rather than a new "Clear all" control. Known limit: a pin older than the 1,000-row scan window is out of reach. Three UI directions were mocked and **C (chip + boundary hairline) was chosen** over a tinted tray and an inline rail. See [`order-inbox.md`](./order-inbox.md) + [`invoices-receipts.md`](./invoices-receipts.md).
- **Claim links — seller keys the order, buyer completes address + payment via WhatsApp link** ✅ (ClickUp `86eyq0epn`, dev) — the TikTok Live funnel (Wagyu Walid, Her Moolah): the seller keys each "mine" claim in Counter Checkout (incl. per-line price overrides, `86eyphh8r`) and **sends the rest of checkout to the buyer** — a WhatsApp link to `/claim/<token>`, a pre-filled **price-LOCKED** checkout where the buyer adds address, date/time and (on the order page next) payment. **A claim is an OFFER**: new `orderClaims` table freezes the lines at send (the session draft is a non-authoritative scratchpad whose prices re-resolve at create, so "locked" needs its own snapshot — pinned by test against a catalog re-price), stock is pre-checked at send but **decrements only at buyer commit** (no reservation until 86eybbxhf; sold-out-at-commit names the line, never drops it silently). **The checkout timer (Zaki's window — revised 27 Aug to the Agoda model)**: a **fixed deadline** picked per send (15 min / 1 h / 24 h chips; the choice becomes the store default `retailers.claimLinkWindowMinutes` — the dialog says so, no hidden Settings card) that runs **until real money**: before commit it gates completion; at commit it carries onto the order as **`orders.paymentDueAt`** (floored to a 15-min payment runway) with the buyer's order page showing the continuing countdown, and a 1-min sweep **auto-cancels a due unpaid order** (stock restored via the shared `applyStatusTransition`, `cancelledReason` stamped so the buyer's page explains itself). One predicate (`isAutoCancelDue`) holds every protection: an "I've paid" claim PAUSES the clock (a human verdict must never race a robot — cancelling a true manual-transfer claim was the rejected outcome), fee-pending suspends it (the buyer can't pay), a live HitPay session shields it AND the mint extends the deadline (visible clock jump — a freeze was rejected as exploitable), and a seller who advanced an unpaid order keeps the robot out. **Resend never resets the clock** and is guarded per claim (5-min cooldown, max 3 sends, `claimResendState` — server rule + disabled-with-reason button from one author). - **One WhatsApp per order — the confirmation is the only automatic buyer send** ✅ (ClickUp [`86eyd63r8`](https://app.clickup.com/t/86eyd63r8), dev) — Meta bills **every delivered message from 1 Oct 2026**, and the lifecycle we'd built (confirm + packed + shipped + delivered + payment-received + mockup + reminders + POD photos + the counter receipt PDF) cost ~**RM0.34/order** ≈ **37% of Starter's RM79** at ICP volume. Gross margin on the wedge plan doesn't survive that. The ticket's per-plan budget table (3 for Starter) was **superseded by one, every plan, every product type**: a budget that varies by tier makes the *buyer's* experience depend on what their seller pays, and "3 messages" still leaves the seller guessing which three they just spent. **The push fires at `orders.create`, always** — no deferral, no timing question. A held total (mockup quote outstanding, `deliveryFeePending`) rides in `{{3}}` as **words**: `PENDING_TOTAL_LABEL` — "to be confirmed" / "akan disahkan", store-locale keyed, chosen at **send** time from the live hold state, so a quote entered between create and send still goes out as a real number. It's a plain text param — the currency code already rides *inside* the value (which is why an SGD store renders "SGD 40.00", not "RM SGD 40.00"), so the body carries a bare `{{3}}`. **Two earlier designs were reversed, and both are worth knowing**: (1) *fire on mockup approval* deadlocked once `notifyMockupSubmitted` was deleted — nothing would tell the buyer a design was waiting, so nobody would approve and the gate would only open on the 48h waiver; (2) *defer, then fire at submit* (86eyfq0w5) fixed that but left the buyer with **no confirmation and no link** from checkout until the seller submitted — possibly days, possibly never — while the order page is the one thing they need, since it's where they approve the mockup. It also **bought nothing** (the price still isn't final when they read it) and cost a state machine: `claimDeferredPush`, five call sites, a `deferred` stamp, a cancel-clears branch in two places, and a buyer-facing card. Saying "to be confirmed" is honest, arrives on time, and **deletes all of it**. **Migration:** `deferred` stays a valid schema literal because rows may still be in it and **nothing claims them any more** — one-shot **`orders:releaseDeferredPushes`** (batched `.take(200)`, idempotent, re-run while `done:false`) must run per deployment or those buyers never get their message; it **sends real WhatsApp**, so it's a deliberate operator action. **Cancel now clears `sending` too**, not just `deferred`: the send action returns early on a cancelled order, so a `sending` stamp would be stuck forever promising a message that can't arrive — reachable far more often now every order starts `sending`. **Removed:** all status updates (packed/shipped/delivered/**cancelled**), custom-stage pings + the per-stage `notify` toggle + `MAX_NOTIFY_STAGES` (this ticket was named as the trigger to re-tune that cap — resolved by deleting it), payment-received, mockup-submitted, the three payment-due prompts, delivery-fee-set, the **day-11 reminder cron**, the counter receipt/invoice **PDF auto-send** (counter 2 → 1), and Lalamove **POD photos** (the only send producing N messages from one event). **The one buyer-side exception is seller-DRIVEN**: the manual payment reminder, hidden days 1–10, live days 11–14 once per 24h (max 4 by geometry), closed forever after — one pure `manualReminderEligibility` drives both the server lock and the button's disabled states. **Seller alerts are a different budget and a different consent** (retailer's own number) and gained a **third** event: a verified HitPay settlement, which previously notified the seller on **no channel at all** — there was no payment-received email either, so the only way to learn money had landed was to open the dashboard. It gets its **own** Meta template, deliberately not a reuse of the claim one whose params otherwise match: a claim asks the seller to check their bank, a settled charge already auto-confirmed the order and needs nothing — reusing it would manufacture work that doesn't exist. Two asymmetries with the claim alert, both deliberate: it is **NOT** fired by `markPaymentReceived` (that *is* the seller, clicking), and it does **NOT** skip cancelled orders (a claim on a dead order is noise; real money landing on one is the urgent case). **The template body names the gateway through `{{4}}`, never as literal text** — Meta freezes body copy at approval, so hardcoding "HitPay" would cost a fresh review cycle when a second gateway lands and, until it got one, would send a Billplz seller to a HitPay account they don't have, on a message whose whole value is *"go look here"*; `receiveGatewayPayment.provider` is **required** (an empty param makes Meta reject the send outright, and requiring it forces a future gateway to identify itself — it caught all seven call sites at compile time). The **env var** stays `WHATSAPP_SELLER_PAYMENT_RECEIVED_TEMPLATE` for the opposite reason: `WHATSAPP_` is a namespace, not a description — none of the nine existing vars name their subject, and there is no `HITPAY_*` namespace to join, since those credentials are BYO per-retailer. This puts the template on the side of the seam the schema already draws (`gatewayPaymentId`, `by_gateway_request` — never `hitpay*`). **Their duplicate emails now self-suppress** via pure `sellerWaAlertWillAttempt`, and the WA action schedules the email back with `force: true` when it gives up — never both, never zero; the WA actions deliberately **don't** force on their own early returns (template unset / toggle off / no number), since the email shares that exact predicate and has already decided not to suppress. **Fixed in passing:** the inbound-`ORD-` **double-send leak** (an old `?send=1` link or a forwarded chat earned a second free-form confirm — now `pushOwnsTheMessage`, with `failed` still replying since that push reached nobody, and `pushRecovered` threaded explicitly because `confirmOrderFromWhatsApp` stamps `recovered` *before* the guard re-reads); the BM `paymentClaimed` subject that read "Pembayaran diterima" (= payment *received*) for an unverified claim, which would have collided head-on with the new sibling; and a **dead config** — sellers could edit "Unknown message reply" in Settings and it was never used in any locale. **`convex/oneMessagePerOrder.test.ts` is the regression gate**: it counts **scheduled** `whatsapp:*` jobs, not fetch calls, because the suite runs on fake timers and a fetch-counting test would read zero and pass vacuously; `NOT_BUYER_SENDS` is a named **subtraction** so an *unknown* new send still trips it, and the seller alerts are asserted **positively** so the exclusion can't rot into a hole hiding their deletion. Note for anyone extending it: "no new send" is asserted as the pending-job count staying **unchanged**, never zero — the create-time job never fires under fake timers. - **Founder business report — Kedaipal's own weekly numbers** ✅ (dev) — Arif had no way to see the *platform's* health (MRR, who lapsed, signups) without hand-assembling it monthly for the `kedaipal-monthly-review` deck, which needs a manual screenshot of the `retailers` table. New secret-guarded `GET /internal/business-report` (`BUSINESS_REPORT_SECRET`, **prod only**; constant-time compare that **hashes both sides first** — unlike the HMAC verifiers, both operands here are the raw secret, whose length is itself secret) → `admin.businessReport` internalQuery → pure `convex/lib/businessReport.ts`. Fetched weekly by a scheduled routine that files a markdown report; **no in-app page** (founder artefact, not a product surface). **MRR is derived from PAID INVOICES, never `planPrice()`** — `subscriptions` has no currency field (currency is picked at issue time and lives on the invoice), so plan constants would count an SGD store's S$59 as RM59; reported **per currency**, never blended, rounded per-subscription so any figure reconciles against one invoice, and an active sub with no paid invoice surfaces as `activeWithoutPaidInvoice` rather than a silent 0. **Churn reads off `past_due`** (manual billing has NO cancellation flow — nothing writes `status:"cancelled"`, so a seller who stops paying just sits there) **but splits FOUR ways**, because a blended number would report losses that never happened: *lapsed customer* (paid before, invoice past due = real churn) / *awaiting payment* (pending invoice not yet due = healthy) / **awaiting your invoice** (paid before, no pending invoice = **Arif's action item**, the cron's Path C exists so a paid vendor never gets free service while waiting on an invoice) / *trial expired* (never paid). The `awaiting_payment` bucket is load-bearing: `issueInvoice` deliberately doesn't touch the subscription and only `markPaid` clears `past_due`, so issuing a renewal leaves the row `past_due` with a **future-dated** invoice — a 3-way classifier would manufacture phantom churn precisely when the right thing was done. `lapsedThisWeek` works with **no schema change** off an invariant worth knowing: for a row *currently* `past_due`, `updatedAt` IS the flip moment (the only other writers move the status away, and the trial-reminder patch deliberately skips `updatedAt`) — **a fourth `db.patch` on `subscriptions` touching `updatedAt` silently breaks it**. Comped rows are excluded *before* classification (the cron's trial path flips them too, unlike the other two) and surfaced as `compedExcluded`; `cancelled` is reported as a **structural** 0 so the number moves on its own the day a cancellation flow ships. Exclusions are three predicates (owner in `ADMIN_USER_IDS` — self-healing; `notifyEmail` fragment; explicit slug list) and **deliberately NOT "unset email"** — `notifyEmail` is optional and independent of the Clerk auth email, so that rule would drop real paying retailers from MRR/GMV; `excluded.slugs` ships in the payload so a wrong exclusion is detectable. Reads are N+1-free (**one** `by_status` collect per invoice status reduced to per-retailer maps, *not* the daily cron's per-subscription `by_retailer` read) and the order scan rides Convex's **system creation-time index** since every `orders` index is `retailerId`-prefixed; newest-first + bounded means a `capped` week under-reports its EARLIEST days, so `capped` must suppress publishing that week's GMV. **`.mcp.json` now defines TWO Convex MCP servers** so the deployment is legible at the call site: `convex` (dev full + prod readOnly) and `convex-prod` (`--prod --cautiously-allow-production-pii`, prod reads unlocked) — otherwise deployment choice is an opaque base64 `deploymentSelector` argument and a tool-approval prompt can't tell you whether an agent is reading dev or live customer data; now the tool NAME says it (`mcp__convex__data` vs `mcp__convex-prod__data`). This is what closes the spec's verification gap (reconcile the report by independent recomputation against prod). **Tools are pruned via `--disable-tools`, because the two prod flags expose an IDENTICAL tool list** (gating is runtime off each deployment's `readOnly` bit) and `--cautiously-allow-production-pii` flips prod to `readOnly: false` — which the CLI help calls read-only-tools-only but the `status` tool's own description says means *all* tools. Rather than resolve that contradiction by attempting a write against prod, `--disable-tools` makes it moot: **`run` off on `convex-prod`** (it invokes mutations AND actions, and our actions reach WhatsApp/Lalamove/HitPay; `runOneoffQuery` is the sandboxed read path, and `run` stays on `convex` since dev mutations are legitimate), **`envGet`/`envList` off on BOTH** (deployment env vars hold `WHATSAPP_APP_SECRET`, the credential-encryption key, HitPay salts — a worse leak than the buyer PII this guards, and one that would land in a transcript; use `npx convex env list --prod`), `envSet`/`envRemove` off, `--dangerously-enable-production-deployments` never set. Deliberate prod writes go through `npx convex run --prod` in a terminal, attributable to a person not an agent turn. **Committed, so it applies to every session in the repo incl. subagents** — prod holds PDPA-relevant buyer data. Replaced, not extended, when HitPay recurring billing (`86eyb6z4r`) brings real cancellation. See [`docs/founder-business-report.md`](./docs/founder-business-report.md).
